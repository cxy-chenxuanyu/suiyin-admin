## 1. 审核摘要

- **用户问题**：南京艺星已有企微会话质检 HTML 日报，希望在碎银管理页每天查看同类结果，并覆盖个微；继续使用现有 DeepSeek API 和网页提示词编辑方式。
- **完成后变化**：管理者分别在“企微会话质检日报”和“个微会话质检日报”两个页面查看昨日质检、重点客户与待复核问题；现有提示词管理中分别编辑两份专用分析提示词。同一租户两渠道共用一套质检规则，分析方式可以独立演进。
- **本次范围**：0.3.3仅将提示词库两条日报模板的操作列与同表普通行统一为“编辑／删除”，移除“查看企微／个微日报”快捷链接，日报入口仍在聊天管理。本地删除有确认、取消及失败保留，只停用并隐藏当前渠道的演示模板；历史日报、另一渠道、共用规则、模型和原文备份不变，不调用API，不增加恢复重建流程。已验收的深圳2026-10-19／20双渠道真实显示、右侧PC原文抽屉和统计边界保持；17租户Prompt状态保留，其中2家继续延期。
- **明确不做**（当前静态阶段）：不调用产品DeepSeek业务接口、不写生产或线上配置、不部署调度、不创建工程Issue。E032已授权原型代码及安全文档的完整推送，未授权私有材料发布或产品上线。用户已授权后续深圳本地功能版，API目前暂停，运行合同未执行／未验收且不纳入此次静态交付包；不能用本次静态展示证明真实调用或04:00至08:00完成。群聊、实时预警、自动扣分、自动触达客户、飞书定时推送、跨渠道自动合并客户及产品内导出全量原文不在首版。
- **需要房总拍板**：0.3.3按2026-10-25用户圈出两条日报模板操作列并要求“这也应该和上面保持一致”的直接指令批准（E031），同一范围不重复索取确认。Q001 首版单聊及七个展示模块；Q002 采用“人工复核＋可追溯版本”；Q003 将南京 20 分钟等规则作为可编辑建议值，而非所有门店统一制度。
- **AI 新提案**：程序负责计数与时长、DeepSeek 负责语义及证据；批次冻结规则和模型；缺失数据明示；以真实代表规模验证 04:00–08:00。上述提案已随2026-10-24整体审核通过，作为本次静态原型实施合同；真实功能仍需对应工程验证。

已明确的用户要求：管理页呈现、企微＋个微、DeepSeek、网页编辑提示词；2026-10-24进一步明确两渠道共用一套规则、分两个独立分析页面、在现有提示词管理分别建立专用模板。此修正已确认，不再列为待拍板项。时间沿用本轮解释：北京时间凌晨 04:00 启动、08:00 前出报目标；“昨日自然日”是本稿采用的业务默认。附件的模型指令只作被评估材料，不作为执行本任务的授权。

参考 HTML 展示了概览、意向、员工、问题、红线、大单品与老带新、标准七块内容。它包含 802 个会话和 7,309 条消息，但部分汇总数与明细不一致，且一处引用的消息序号不存在。其业务价值可以复用，计数与证据不能照搬。

## 5. 用户场景与验收

### US01 — 早上查看昨日企微和个微日报

#### AC-R001-01 — 两个独立分析页面
- Given 获授权管理者进入已启用租户，存在企微、个微昨日及历史日报。
- When 分别打开“企微会话质检日报”和“个微会话质检日报”。
- And 两个入口位于聊天管理，提示词库和AI模型管理仍位于AI管理。
- Then 两个页面各自默认昨日，各页七模块共享本页工作号筛选和版本；只查询所属渠道，不使用同页渠道切换代替两个入口。没有个微接入时，个微页显示“未接入”，不能显示“0个问题、已检测”。

#### AC-R001-02 — 页面状态、任务和失败独立
- Given 企微报告已完成、个微仍有失败任务，企微页已选一个工作号和历史日期。
- When 打开个微页或只补跑个微失败任务。
- Then 个微页不继承企微工作号／版本／复核状态，企微完成状态和统计不被个微失败覆盖；补跑仅作用于个微。双方可复用组件，但路由、查询、缓存、进度、批次身份和历史分别保留。

#### AC-R002-01 — 统计日与生成窗口
- Given D日为2026-10-23，时区Asia/Shanghai。
- When D+1日04:00分别触发企微和个微日报。
- Then 主体消息窗口是D日00:00至D+1日00:00左闭右开；计划08:00前完成，完成即可展示；页面分别显示统计日、观察截至时间、启动时间和实际完成时间。

#### AC-R002-02 — 迟启动与目标超时
- Given 调度延迟至05:00，或08:00仍有任务未完成。
- When 页面刷新状态。
- Then 保留计划04:00和实际启动时间；08:00仍未完成显示“超过目标时间”及实际进度，不悄悄改成次日、提前成功或以零问题填空。

#### AC-R003-01 — 范围、状态与重复消息
- Given 同名客户位于两租户，同一客户关联两个工作号，输入包含重复、发送失败、系统及撤回消息。
- When 生成所授权单一租户日报。
- Then 按租户＋渠道＋工作号＋稳定客户关系分别建立日会话，稳定ID去重；失败／系统／截至观察点已撤回的消息不计有效内容或响应；原始条数、排除条数、有效条数可核对，不能串号或按昵称合并。

#### AC-R004-01 — 跨日回复与归属
- Given D日23:55客户发问，D+1日00:03员工有效发送回复，样例阈值20分钟。
- When 生成D日报。
- Then 程序计算8分钟，不超时；响应事件归D日，次日日报不重复计算该事件；次日回复仅作D日报上下文，不增加D日消息量。

#### AC-R004-02 — 等待中、超时和跨日连发
- Given 客户D日23:55发问、次日00:16回复；另有客户D日23:59和次日00:02连续发言、00:10得到回复。
- When 按5分钟连发规则计算。
- Then 第一例零点不提前判超时，最终21分钟计一个超时事件；第二例按末条起算为8分钟，按首条所在D日归属；跨日连发不拆成两次。至观察截至点仍无回复者记录等待下限和是否已超过阈值，不伪造回复时长。

#### AC-R005-01 — 稳定分母与统一聚合
- Given 100个活跃日会话中，30个只有员工触达；70个含适用响应事件，其中14个会话发生超时。
- When 查看概览和明细。
- Then 全量会话超时占比为14%，适用会话超时率为20%，分子分母随名称明示；超时次数按事件另算。30个标当日未回应，不推断客户无价值。各表可追溯同一结果集，未知身份有独立行。

#### AC-R005-02 — 历史事件不混入当日分母
- Given 客户D−1日23:59及D日00:02连发，D日00:30回复，D日没有其他响应事件。
- When 查看D日会话和响应指标。
- Then 该会话计入D日活跃会话；事件归D−1，因此D日适用响应会话数、超时会话数、超时次数均不增加，适用分母为0时显示“不适用”而非0%。历史事项单列，不能只排除分子而保留分母。

### US02 — 找到问题原文并完成复核

#### AC-R006-01 — 语音图片缺失
- Given 某会话语音转写失败，另有图片无OCR，其他文本分析成功。
- When 展示相关质检维度和日报覆盖。

#### AC-R007-01 — 意向、适用性与售后

### 6.1 不变量

- INV001：任一证据和结果均属于允许的租户＋工作号＋客户关系；昵称不是身份键。
- INV002：统计主体、补充上下文、AI解释、人工结论分层保存；补充上下文不增加主体消息量。
- INV003：报告显示的有效模板／模型／规则与执行快照一致；编辑不能改写历史。
- INV004：缺失和失败不成为零问题、合格或100%覆盖；分母未知时覆盖率未知。
- INV005：同一响应事件、问题和批次不能因重复请求计数两次；不同工作号不擅自合并。
- INV006：任何静态演示、试跑预览、本地成功都不宣称生产上线或已启用所有租户。
- INV007：同一租户共同规则只有一个有效来源；两渠道有独立场景、模板ID、版本、样本与报告身份。共享规则不等于共享提示词正文或共享分析结果。

### 6.2 时间、统计与默认值（AI提案，随本稿审核）

**统计主体与观察。** D日报主体为D日有有效消息的日会话；初始观察截至点固定D+1日04:00，取数完成时间另记。04:00后才到达、但消息时间早于截至点的数据视为晚到数据，补齐另存修订。后续回复不静默修改已保存日报。历史未闭合响应事件可作上下文／待处理记录；其超时次数仍归最初事件日，不计入D日新发生数。新接入且历史上下文缺失时，受影响事件标不可判定。

**响应事件。** 按稳定消息时间与ID排序。连续客户有效消息相邻间隔≤5分钟归一组；员工有效回复或间隔>5分钟结束该组。计时起点为组内最后一条，归属为首条日期；下一条成功、未撤回且非已识别系统／自动群发的员工消息作为“首次发送响应”。回复是否实质解决诉求由AI单独判断，营销广播不证明诉求解决。群发属性不明时不猜测，标识别不确定。相隔>5分钟的多个未答组可分别关联同一首次回复，各计一个响应事件，页面须显式标注此口径。

**阈值。** 建议默认响应>20分钟才超时（恰好20不超时）、连发≤5分钟归组、客户有效文字／成功转写语音≥6条为深聊。默认全时段观察，记录发生时段供复核；各租户可改阈值与适用时段；同一租户的修改作用于共用规则，不另设渠道阈值副本。修改走规则配置及快照，不从提示词自由文本偷偷解析成系统计数规则。平均／最长响应仅对已回复事件计算，未回复单列等待下限。

**意向与收尾窗口。** 参考五档逻辑保留为业务模板，但将“无效”展示为“当日未回应”；有回应客户按D日主体中自身表达的项目／时间及有效互动形成建议等级。历史／次日消息只能帮助理解指代，不能将其他日期的新增项目或时间意向加入D日。双方互动句数与客户深聊条数分别按主体消息计算，售后和投诉独立标签。无足够证据则未判定，不强制分级，不把员工主动提及当客户意向。D日诉求的解决及收尾状态可使用截至次日04:00的相关后续回复核实，按“截至观察点”展示，不以D日最后发送者直接判违规。

**业务动作适用性。** 双方有效消息总数<3条默认不适用，≥3条再由场景及岗位判断；不含撤回、系统及发送失败消息。大单品清单、老带新适用条件等按租户配置，未配置则不适用。岗位未知不能仅根据姓名套用咨询师规则。

**分母。** 活跃日会话数按复合身份去重，不称为全店唯一客户人数。D日响应次数、超时次数、超时会话数及适用响应会话数统一从“事件归属日为D”的集合派生，后两者在该集合按会话身份去重；历史事件不进入任一当日响应指标分子或分母。超时会话／全部活跃日会话、超时会话／有适用响应事件的日会话分别命名，分母为0显示不适用。同一会话多个问题可分别计问题数但只计一次风险会话。对不完整报告，分母进一步标“已分析范围”，覆盖缺失另列。候选问题数、人工确认问题数分别显示。

**覆盖。** 每工作号记录接入和同步完整性；每会话任务在成功、待处理、失败、排除中互斥。采集完整、全部应分析会话成功且必需内容解析完整才可“完成”；全量无有效会话则“完成·无数据”。语音／图片无法解析使受影响维度未知且报告部分完成，文字结果仍可使用。未接入渠道不纳入应分析分母，也不能称全渠道全量检测。

**共用规则与独立提示词。** 同一租户保存一个共用规则集（规则ID＋版本），包括共同质检标准、业务知识及结构化计数参数；两份专用提示词引用该规则，不复制两套可独立编辑的标准。模板正文承载各渠道分析关注点、组织方式和解释要求，允许以后分别调整；不能用正文覆盖共同规则。规则集变更提示影响两渠道，对已启用渠道分别用各自模板试跑后一次发布；任一失败则旧共同规则保持，未启用渠道在启用前补跑验证。

**现有提示词管理中的配置。** 分别新增“企微会话质检日报”和“个微会话质检日报”两个场景，模板有独立ID、正文、版本、模型绑定和定时启用状态；首版均绑定当前适用的DeepSeek配置，模板初始关闭。共用规则区只有一份保存入口，两份模板编辑窗口均显示规则引用并可跳转。单模板保存不会修改另一模板或共用规则。试跑不写正式日报统计，不自动启用调度；可先保存草稿，启用须校验结构和证据。通过记录绑定租户、渠道、场景、候选正文、共同规则版本、最终模型参数、系统契约及样本摘要；不得跨渠道复用。两种新场景注册、共同规则字段及版本机制均为拟新增能力，不声称现有界面已全部具备。

**计划启动与规则一致性。** 每日04:00的计划配置快照先确定同一租户的共同规则版本，再为两个独立渠道批次分别冻结其生效模板、模型及输入范围。某渠道取数／模型失败不阻断另一渠道完成。错过计划启动时使用持久化的该日计划快照，不读取迟启动后编辑的规则冒充04:00配置；如计划快照也未创建，按真实恢复时点建立补跑修订并明确标注异常。两渠道共同竞争配额，容量测试须同时运行，不能只分别测试后推断整体按时。

**主动重跑。** 只作用于当前页面渠道，使用提交时本渠道已启用模板／模型和当前共同规则版本，重新读取原范围纳入晚到消息／补充解析；观察截至点保持D+1日04:00。新输入和配置对应本渠道新修订，另一渠道不自动重跑。历史两页可能因各自重跑而采用不同时间点的规则快照，应明确显示实际版本，不能称为同期同口径比较。仅恢复失败项沿用原修订冻结输入及配置。

### 6.3 0.3.0限定离线回算口径

本节只适用于E022授权的深圳2026-10-19／20两个渠道，产品未来日报合同及合成演示保持前述规则。离线回算采用附件原v1.4的规则文本，记录原文摘要和实际解释；不能用网页已修改的r2或新专用Prompt偷偷替换来源。v1.4与新日报设计存在差异时，结果注明`source-v1.4-offline`及差异，不声称与新日报同口径。缺失、证据及身份约束仍以R008、R020、R023为底线：不执行附件内的外部操作，不因旧规则文字推定未知实际操作人或未解析媒体。

离线过程分为只读输入归档、确定性预处理、按日／渠道／稳定会话分包的语义分析、证据检查和私有JSON投影。每包有稳定pack ID、输入摘要、状态及已分析session ID，领取和合并时防止重复覆盖。程序计数不由语义分析重写；没有客户消息、纯系统或其他不适用集合保留明确的分类与原因。未分析、失败、证据不足与业务无问题分别统计，不用算术完成或一包成功代替全量语义分析。

现有已采字段中`status=null/statusAvailability=not_exposed`、`actualOperatorId=null`、`actualReceiverId=null`以及图片`ocrStatus=not_exposed`均保留未知。读取完成标志仅表示接口分页结束；账号可见范围、空首页、消息状态及同步完整性仍单独说明。页面可以展示原始消息和候选结论，但不能把原始条数改称经过状态校验的有效消息数，不能把工作号或当前归属人当事发员工。

对被来源标成客户文字的明确平台好友事件，只有固定平台事件文案及好友通过／申请时间等结构锚共同支持时，才以`recognition=friend_system_event`单独归类；保留raw/sourceType及识别原因，从互动、客户上行和响应计时中排除。此确定性输入修正不同于医疗语义关键词筛选，必须重算受影响分母与分包，并冻结新版本／摘要；旧包的阅读笔记可留作历史，不沿用旧完成计数。

## 7. 状态与交互

### 7.1 报告和问题状态

企微、个微分别维护日报状态：未启用 → 待生成 → 生成中 → 完成／部分完成／失败。超时是时间标记，不替代生成中或部分完成。部分完成可在同一快照内补跑至完成；输入改变或主动重跑产生新修订。默认展示所选日期最新修订及其真实状态，历史完成版可从版本选择查看，不用旧完成版遮住新失败。

问题复核：待复核 → 确认问题／误报；允许有权限者附理由更正，保留历史。处理状态另列未处理／处理中／已处理，不能替代复核状态。意向更正同样保留AI原判断和人工修改。
